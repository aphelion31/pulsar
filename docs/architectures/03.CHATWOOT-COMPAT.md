# 03. Chatwoot compatibility

## Schema

`migrations/0001_schema.sql` is generated from Chatwoot's `db/schema.rb` by `tools/schema2sql.rb`, a small
stub of the ActiveRecord schema DSL that prints SQL. It needs no Rails install:

```bash
ruby tools/schema2sql.rb ../chatwoot/db/schema.rb > migrations/0001_schema.sql
```

Regenerate `0001_schema.sql` when Chatwoot's schema changes, then check the handlers that read changed tables. The schema
needs the `vector`, `pg_trgm` and `pgcrypto` extensions. Pulsar targets **Chatwoot `v4.20.1`** (schema version `20261125100456`, applied cleanly on top of older schemas via `migrations/0008_chatwoot_4_20.sql`).

## Auth

`users.tokens` holds devise_token_auth entries `{client_id: {token: hash, expiry}}`; Pulsar uses **Argon2id** (`m=19456, t=2, p=1`) for new passwords and session tokens while transparently verifying legacy `bcrypt` hashes (`$2a$`/`$2b$`/`$2y$`) and upgrading them on login. `access_tokens` rows work as `api_access_token` headers for API clients and agent bots.

## API shapes

Handlers return the JSON the Chatwoot jbuilder views produce, including enum names (`"open"`, `"resolved"`),
unix-second timestamps and `display_id` as the public conversation id. Realtime events use the names and
payloads of Chatwoot's `ActionCableListener`.

## Differences from Rails Chatwoot

- Single-binary Rust + PostgreSQL runtime without Redis or Sidekiq (`pulsar_events`, scheduled timers, and in-process async listeners replace Sidekiq queues).
- Unmatched API routes return HTTP `501` (`Not Implemented`) intentionally rather than silent 404s.
