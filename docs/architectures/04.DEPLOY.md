# 04. Deploy

## Build

```bash
cargo build --release                 # target/release/pulsar, about 9 MB
(cd web && pnpm install --frozen-lockfile && pnpm build)   # web/build/client
```

Build Linux release binaries for glibc (`x86_64-unknown-linux-gnu`). The musl target works, but musl's
allocator fragments under load (RSS grew past 600 MB in the benchmark, glibc stayed at 18 MB).
Cross-build from macOS with `cargo zigbuild --release --target x86_64-unknown-linux-gnu.2.31`.

## First run

```bash
createdb pulsar
psql -d pulsar -f migrations/0001_schema.sql
# Pulsar additions, idempotent and safe on an existing Chatwoot database (0002 builds indexes CONCURRENTLY)
psql -d pulsar -f migrations/0002_pulsar_indexes.sql
psql -d pulsar -f migrations/0003_pulsar_widget_token_floor.sql
DATABASE_URL=postgres://.../pulsar ./target/release/pulsar seed admin@your-domain 'a-long-password' "Your company"
```

## Run

```bash
DATABASE_URL=postgres://user:pass@host/pulsar \
SECRET_KEY_BASE=$(openssl rand -hex 64) \
FRONTEND_URL=https://support.your-domain \
WEB_DIR=/srv/pulsar/web \
STORAGE_DIR=/srv/pulsar/storage \
BIND=127.0.0.1:3000 \
./pulsar
```

Put a TLS reverse proxy (Caddy, Traefik, nginx) in front. It must pass websocket upgrades on `/cable`.
Keep `SECRET_KEY_BASE` stable across restarts: changing it invalidates every file URL and widget visitor token.
Back up the database and `STORAGE_DIR` together.

## Existing Chatwoot database

Point `DATABASE_URL` at a copy of the Chatwoot database first. Users keep their passwords and tokens. Uploaded
files are readable if `STORAGE_DIR` points at Chatwoot's `storage/` folder (disk service only).
Stop Chatwoot's Sidekiq before pointing production at Pulsar, so two systems do not process the same data.
